# 09 — Feature parity matrix (kvadro² → HOMI)

Every user- or operator-meaningful capability of kvadro² (bot `@KvadroAppBot`, Mini App `app.kvadro.app`, landing and SEO
pages `kvadro.app`) as a feature `F-<MODULE>-NNN`, with its legacy evidence, its HOMI target, its migration decision and
checkable acceptance tests; plus the deviation register (`DEV-NNN`) required by the migration policy in
[README](README.md#migration-policy). `data/features.csv` holds the same rows in machine-readable form — change both together.

Status: **compiled 2026-11-09 from the wave-1 audits** (01, 02, 03, 03b, 04, 05, 06, 08, 10). Nothing here is approved: every
target that depends on an open conflict (`CF-…`, `10` §2.1 — all twenty are open) is marked `PROPOSED`, and every `DEV-…` is
`PROPOSED` until the developer approves it. Business rules are compiled in [07](07-business-rules.md).

## 1. How to read the matrix

| Column | Meaning |
| ------ | ------- |
| feature_id, module, feature | Stable id (never renumbered), module, short name. |
| user_role, user_flow | Who uses it and the shortest description of the flow. |
| legacy_source, legacy_behavior | Where the legacy behaviour lives (paths under `$KVADRO_ROOT/demo/app/src`, `$KVADRO_ROOT/docs/*.md`, landing files) and what it does, short and precise. |
| api_dependencies | `API-…` / `RES-…` the feature calls or serves (`08`). |
| db_dependencies | Logical entities from `06` (`ENT-…`). |
| new_backend, new_frontend | HOMI module/route and app/screen, consistent with `10` §2; "(CF-NNN A — PROPOSED)" = the recommended option of an open conflict. "Legacy Mini App unchanged" = the recovered client keeps running against the compatibility surface (CF-011 A). |
| telegram | `bot`, `Mini App`, `bot + Mini App` or `none`. |
| priority | **P0** — needed by the compatibility backend the running Mini App and bot use at the backend cut-over (every API/RES the old client calls, every bot handler and outbound job, the pipeline feeding them, the privacy promises). **P1** — other surfaces the legacy backend serves that must not go dark at its switch-off (landing data, uz/en landing, SEO, CSV, sitemap) and operator parity before the new frontend. **P2** — client behaviour rebuilt in the new Mini App/landing (the old client keeps doing it meanwhile). **P3** — dev-only, cosmetic or drop candidates. |
| status | Weakest status of the evidence that defines the behaviour: the linked ids (API rows use their *server-logic* status) and the business rules mapped to the feature in `07`. `DEPRECATED_CANDIDATE` only where the feature itself is probably obsolete. |
| migration_decision | `MIGRATE` (carry 1:1), `MIGRATE_WITH_FIX` (carry, with the listed `DEV-…` and/or defect fixes), `REBUILD` (capability kept, mechanism changes per a CF/GAP), `DEFER` / `DROP_CANDIDATE` (need a decision — the cell names who decides). |
| dev_ids | Deviations in §4 that change this feature on purpose; parity tests expect the new behaviour. |
| linked_ids | Every `SCR/API/RES/BOT/BTN/LND/URL/TMA/TXT` id the feature covers. `TXT-BOT-…` ids are added from the BOT/BTN rows that use them. |
| evidence | `doc:line (id)` of the first linked items (`02`, `03`, `03b`, `04`, `05`, `08` = the audit docs), then the rules (`BR-…`), legacy bugs (`LB-…`) and security findings/requirements (`SEC-…`, `SEC-REQ-…`, `16`) attached to the feature. |
| acceptance_tests | Concise, checkable statements for contract, characterization or E2E tests (`15`). |

Module names follow the audit vocabulary, with two additions: **COMPAT** (the legacy API dialect the running Mini App needs,
CF-001) and **LOCALE** (internationalisation; spelled without digits because `scripts/migration/collect_ids.py` recognises
feature ids only as `F-[A-Z]+-NNN`).

## 4. Deviation register

Every legacy bug or questionable decision (`LB-…`) ends up in exactly one of two places:

- a **`DEV-NNN` row** (§4.2) when its fix changes behaviour that a user, the still-running legacy Mini App, old bot
  messages or a public link can observe. All DEV rows are `PROPOSED`: the developer approves them (and the named co-decider
  where money, permissions, privacy, SEO or a shared ADR is touched). Parity tests expect the new behaviour only after approval.
  Approved so far in this register: DEV-051, the Mini App's dates of DEV-014 and the halves of DEV-010, DEV-016 and DEV-017
  that legacy adopted (DEC-58); DEV-053 (DEC-67).
- a **"defect fix, no DEV" row** (§4.3) when the fix removes a crash, a hang, wrong data, a security weakness or an
  internal/API-shape problem and changes nothing a user or a legacy client relied on. These are `APPROVED` by the migration
  policy itself; the fix is still tested.

Fixes on the client side (LB-APP) apply to the new HOMI Mini App only — the recovered legacy client is not modified. Fixes on
the bot side (LB-BOT) apply to the rebuilt bot; buttons in messages sent before the cut-over reach the callback catch-all
(F-BOT-013) unless the legacy `callback_data` grammar becomes known (Q-BOT-017).

## 5. Two-way coverage

Mandatory in both directions. Forward: every `SCR`, `API`, `RES`, `BOT`, `BTN`, `LND`, `URL` and `TMA` id defined in
`data/ids.csv` (and every `TXT-BOT`) appears in `linked_ids` of at least one feature. Reverse: every linked id exists; every
`LB-…` lands in exactly one of §4.2 (DEV row) or §4.3 (defect row); every `BR-…` in `07` names at least one feature that
exists here.

Since the intake of `index-CBlEKxdL.js` (2026-11-19) the coverage is incomplete for exactly the ids that intake added to
the audit (listed in §2): their feature rows, `DEV` rows and defect rows come with the owner-cabinet plan. The ids of the
intake of `index-CIa0Ldj2.js` are covered forward (SCR-063, API-055, TMA-047).

The check ran with a throw-away script kept outside the repository (the compiling session's scratch area; it is not
committed). Its forward part is reproducible from the repository root with this one-liner (regenerate the index first with
`python3 scripts/migration/collect_ids.py`):

```bash
python3 -c "import csv;ids=list(csv.DictReader(open('docs/migration/data/ids.csv')));cov={i for f in csv.DictReader(open('docs/migration/data/features.csv')) for i in f['linked_ids'].split()};[print(k,sum(r['id'] in cov for r in ids if r['kind']==k),'/',sum(r['kind']==k for r in ids),[r['id'] for r in ids if r['kind']==k and r['id'] not in cov]) for k in ['SCR','API','RES','BOT','BTN','LND','URL','TMA','TXT-BOT']]"
```

## 6. Maintenance

- New features take the next free number of their module; ids are never reused. A removed feature stays with
  `DEPRECATED_CANDIDATE`.
- A new `LB-…` item in any audit needs a DEV row or a defect row here; a new `SCR/API/RES/BOT/BTN/LND/URL/TMA` id needs a
  feature. Re-run the coverage check of §5 after every change and paste the new result.
- The ids added by the intake of `index-CBlEKxdL.js` (2026-11-19, listed in §2) have no feature rows, `DEV` rows or defect
  rows yet: these come with the owner-cabinet plan.
- When the developer approves a DEV, change its status to `APPROVED` here and in the parity tests; when a CF is decided,
  drop the "— PROPOSED" marker from the targets that depend on it.
