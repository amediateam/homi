«Ты» — основная сессия Claude Code. Её модель — та, с которой разработчик запустил сессию (ожидается Claude Fable 5.1).

- Пиши `session-handoff.md` после каждой фазы и перед любым шагом с большим объёмом чтения — до того, как контекст заполнится, а не после.
- Субагентам передавай Task Contract и пути, а не содержимое репозитория.

# 3. PACKAGE FIRST — COMPOSER INTELLIGENCE SYSTEM

Это одно из самых важных требований проекта.

Claude Code и все AI-агенты должны знать, какие Composer-пакеты уже доступны, что они умеют и как их правильно использовать.

## 3.1. Первоначальный аудит

Изучи реальный `composer.json`, `composer.lock` и установленные зависимости.

Для каждого обнаруженного пакета определи:

- Название.
- Установленную и заявленную версии.
- Назначение.
- Основные возможности.
- Где он используется.
- Какие модули HOMI могут его переиспользовать.
- Ограничения совместимости.
- Состояние поддержки.
- Известные важные риски.
- Наличие официальной документации.
- Наличие соответствующего Laravel Boost Skill.

Не придумывай список пакетов. Реестр должен отражать фактические зависимости проекта.

## 3.2. Package Capability Registry

Создай:

`/docs/backend/package-registry.md`

Пример структуры записи:

| Package | Version | Capabilities | Current Usage | Reuse |
|---|---|---|---|---|
| Обнаруженный пакет | Фактическая версия | Поддерживаемые функции | Реальные места использования | Возможности повторного применения |

Создай также машиночитаемый индекс, если это упрощает автоматизацию.

Используй детерминированную генерацию данных из Composer, а не AI-догадки.

## 3.3. Обязательное правило каждого backend-задания

Перед реализацией новой backend-функции:

1. Определи требуемую возможность.
2. Проверь встроенные возможности Laravel и PHP.
3. Проверь Package Registry.
4. Проверь существующий код HOMI.
5. Проверь Reference Codebase `app.uz`.
6. Изучи документацию подходящего пакета.
7. Определи, можно ли использовать имеющееся решение.
8. Только после этого принимай решение о новой реализации.

Например, если уже есть пакет для authentication, permissions, media management, HTTP, caching или validation — сначала исследуй его реальные возможности.

Не устанавливай новый пакет, если подходящий уже есть.

Не создавай собственную инфраструктуру поверх встроенной функциональности Laravel без обоснованной необходимости.

## 3.4. Поддержание актуальности

Package Registry должен обновляться при изменении:

- `composer.json`;
- `composer.lock`;
- фактически используемых пакетов.

Для каждого нового задания используй актуальный сохраненный индекс зависимостей и проверяй, не устарел ли он.

Не заставляй агента перечитывать весь Composer dependency graph при каждой простой задаче.

Реализуй автоматическое обнаружение изменений зависимостей через checksum, Git diff или сопоставимый механизм.

Отдельно проверяй security advisories и совместимость.

## 3.5. Запрет на изобретение велосипеда

Запрещается:

- Создавать собственный пакет вместо подходящего установленного.
- Дублировать встроенные механизмы Laravel.
- Добавлять вторую библиотеку с той же функцией без обоснования.
- Копировать vendor-код в проект.
- Оборачивать каждую библиотеку в ненужные дополнительные абстракции.
- Выполнять массовый рефакторинг только ради применения нового паттерна.

**Не требуется использовать абсолютно каждый установленный пакет. Требуется максимально эффективно использовать подходящие пакеты.**

## 3.6. Детерминированная генерация реестра

Источники данных для реестра — команды, не догадки:

- `composer show --format=json` — установленные пакеты и версии;
- `require` / `require-dev` в `composer.json` — прямые зависимости (в реестр входят прямые; транзитивные — только если используются в коде напрямую);
- `composer licenses` — лицензии;
- `composer audit` — security advisories;
- `composer outdated --direct` — отставание версий;
- `rg -l "Vendor\\Package"` по `backend/app` — фактические места использования.

Реализуй генератор `scripts/packages/registry` (PHP или shell — по стеку), который пересобирает таблицу и сохраняет checksum `composer.lock` в шапке файла. Колонки, заполненные AI-резюме (Capabilities, Reuse), помечай `[ai-summary]`, чтобы отличать их от детерминированных данных.

## 3.7. Соотношение реестра и памяти

- `/docs/backend/package-registry.md` — канонический полный реестр.
- `.ai/memory/package-capabilities.md` (раздел 11) — компактный индекс: пакет → одна строка → ссылка на реестр. Генерируется из того же источника, вручную не редактируется.

Не веди два независимых списка пакетов.

## 6.5. Решения, которые принимаются один раз (ADR в Phase 1–2)

Эти решения затрагивают все приложения и дорого переделываются — прими их до настройки окружения и зафиксируй как ADR:

- **Пиннинг версий**: `.node-version`/`.nvmrc`, поле `packageManager` в корневом `package.json` (corepack), `config.platform.php` в `composer.json`.
- **Frontend monorepo**: pnpm workspaces для `frontend/`; Turborepo или аналог — только при подтверждённой пользе.
- **Драйверы queue/cache/session**: Redis не входит в заявленный стек — по умолчанию `database`; Redis только через ADR с обоснованием.
- **Время и локали**: хранение времени в UTC, отображение в `Asia/Tashkent`; если `about.md` требует несколько языков интерфейса (uz/ru/…) — подход к i18n и к переводимым полям БД решается здесь, так как влияет на схему.
- **Версионирование API**: префикс `/api/v1`.

# 7. CDN.HOMI.UZ — S3 STORAGE INFRASTRUCTURE

## 7.1. Основной источник

Прочитай:

`/Users/shohsanam/Documents/Development/Server/nginx/31.220.104.38/docs/cdn-deploy-guide.md`

Сначала выясни:

## 7.2. Основное назначение

`cdn.homi.uz` используется для хранения и доставки изображений и других разрешенных публичных медиафайлов.

Разделяй:

- Public media.
- Private files.
- Temporary uploads.
- Processed images.

Приватные файлы нельзя автоматически делать публичными через CDN.

## 7.3. Laravel Integration

Используй Laravel Filesystem и S3-compatible adapter.

Сначала проверь, имеется ли нужный Flysystem/S3 пакет в Composer.

Если пакет уже установлен, используй его.

Не создавай собственный S3-клиент без причины.

Поддержи:

- file upload;
- file validation;
- temporary upload URLs;
- public URLs;
- private signed URLs;
- object deletion;
- metadata;
- image variants;
- image optimization, если требуется.

Для больших файлов оцени прямую загрузку в S3 по подписанным URL без пропускания всего файла через PHP-сервер.

## 7.4. Image Pipeline

Проектируй безопасную обработку:

**Upload → Validate → Store → Process → Publish → Deliver.**

Предусмотри:

- MIME/content validation;
- ограничения размера;
- ограничения размеров изображения;
- защиту от опасных файлов;
- уникальные object keys;
- нормализацию ориентации;
- создание необходимых размеров;
- WebP/AVIF при подтвержденной пользе;
- background processing;
- retry failed jobs;
- удаление временных файлов;
- корректное кеширование;
- очистку старых вариантов.

Не создавай десятки размеров изображения без необходимости.

## 7.5. Performance

Используй правильные:

- Cache-Control;
- ETag;
- Content-Type;
- Content-Disposition;
- cache invalidation;
- immutable asset URLs, где применимо;
- responsive images;
- lazy loading;
- preload для критичных изображений.

Избегай загрузки оригинальных огромных изображений для маленьких UI-превью.

## 7.6. Environment Separation

Local, Staging и Production не должны случайно использовать один и тот же writable bucket.

Используй отдельные bucket или строго изолированные prefixes с ограничениями доступа.

Поддержи локальную разработку без обязательного подключения к production S3.

Не храни access keys в Git.

# 8. HOOK.HOMI.UZ — TELEGRAM WEBHOOK INFRASTRUCTURE

Настрой отдельный публичный домен:

`hook.homi.uz`

Назначение — безопасный прием Telegram Bot API updates.

Предпочтительный вариант — отдельный virtual host/reverse proxy, направляющий запросы в существующее Laravel-приложение.

Не создавай отдельный backend или микросервис без причины.

## 8.1. Webhook Design

Реализуй архитектуру:

**Telegram → HTTPS Webhook → Verify → Deduplicate → Durable Queue → Process → Log/Monitor.**

Используй стандартные Laravel capabilities и уже установленные пакеты.

## 8.2. Security

Обязательно:

- HTTPS;
- проверка `X-Telegram-Bot-Api-Secret-Token`;
- безопасное хранение bot token;
- ограничение размера входящего запроса;
- валидация структуры событий;
- запрет раскрытия секретов в логах;
- проверка полномочий для связанных действий;
- разделение bot tokens по окружениям.

Не считай секретный URL достаточной аутентификацией.

Не полагайся исключительно на IP-фильтрацию.

## 8.3. Reliability

Предусмотри:

- дедупликацию по идентификатору бота и `update_id`;
- быстрый ответ после надежного принятия события;
- асинхронную обработку;
- retries;
- контроль повторных событий;
- мониторинг ошибок;
- failed jobs / dead-letter handling;
- безопасную повторную обработку;
- защиту от перегрузки;
- traceability конкретного update.

Не подтверждай получение события до надежного сохранения задания, если потеря update недопустима.

Обработка должна быть идемпотентной.

## 8.4. Multiple Environments

Раздели:

- development bot;
- staging bot;
- production bot.

Локальный домен `.loc` недоступен серверам Telegram.

Для локальных интеграционных проверок используй отдельный тестовый бот и защищенный HTTPS tunnel, когда это необходимо.

Не меняй webhook production-бота без явного разрешения.

Подготовь безопасные команды регистрации и проверки Telegram webhook.

## 8.5. Documentation

Создай:

`/docs/infrastructure/telegram-webhook.md`

Добавь инструкции:

- конфигурация;
- регистрация webhook;
- проверка статуса;
- диагностика;
- тестирование;
- обработка повторов;
- мониторинг;
- ротация секретов;
- восстановление после ошибок.

## 8.6. Практический чеклист

- Регистрация webhook — с `secret_token`, явным `allowed_updates`, разумным `max_connections`; `drop_pending_updates` — только для dev/staging.
- Команды `telegram:webhook:set|info|delete` отказываются работать с production-ботом без явного флага подтверждения и соответствующего `APP_ENV`.
- Хранилище дедупликации (`bot_id` + `update_id`) — с TTL; механизм выбирай из уже доступных (БД/кеш), новую инфраструктуру не добавляй.
- Логи webhook содержат `update_id` и request ID, но не содержат токен и персональные данные сверх необходимого.

## 9.5. Механизм делегирования (реальный, не симулируемый)

**Внутри Claude Code:**

- Субагенты описываются в `.claude/agents/<name>.md` с frontmatter: `description` (триггер маршрутизации), `tools` (минимальный набор), `model` (допустимые значения проверь в установленной версии Claude Code). Это и есть реализация модельного роутинга из 9.1.
- Read-only исследование — субагент типа Explore (без Edit/Write).
- Параллельные исполнители работают в отдельных Git worktrees (раздел 14): один worktree — один агент — один Task Contract.
- Результаты субагентов — только в формате контракта (9.3), без свободного пересказа.

**Внешние агенты (Codex, Gemini, Grok и другие):**

- Вызываются через обёртки `scripts/agents/<tool>.sh` с единым интерфейсом: контракт на вход (файл или stdin) → результат-контракт на выход; неинтерактивный режим; таймаут; рабочая директория — только выделенный worktree; секреты в окружение не передаются.
- Доступность проверяется в Phase 0: `which`, `--version`, одна тестовая задача на 1–2 строки. Нет обёртки или она не прошла проверку — агент считается недоступным, используется fallback на Claude-субагента, факт фиксируется в Cost Registry.

## 9.6. Расширенные поля контракта

Поля `AGENT`, `MODEL`, `WORKTREE`, `BUDGET` (максимум итераций, таймаут, лимит токенов — если измерим) и `DEPENDS_ON` делают контракт достаточным для 9.2 без дополнительного контекста. В ответе `ITERATIONS`, `DURATION`, `TOKENS_USED` (только фактические данные инструмента) и `VERIFIED_BY` питают Cost Registry (раздел 19) и приёмку.

Контракты хранятся в `.ai/tasks/<TASK_ID>.md`; формат `TASK_ID`: `HOMI-<area>-<nnn>` (например `HOMI-cdn-003`).

## 9.7. Лимиты по умолчанию

Действуют, пока не переопределены в контракте:

- не более 3 итераций исправления одной задачи — затем возврат координатору с новым контрактом или эскалация человеку;
- не более 3 параллельных агентов на этапе настройки;
- эскалация на более дорогую модель — только после задокументированной неудачи более дешёвой;
- задача, дважды не прошедшая приёмку, не «допиливается» на месте — переформулируется контракт;
- критические задачи (миграции, auth, безопасность, инфраструктура) принимает независимый субагент-ревьюер, не видевший процесса реализации.

- разрешенные файловые пути;
- риск утечки секретов.

Read-only MCP по умолчанию предпочтительнее write-доступа.

## 10.5. Конкретика для Claude Code

**`CLAUDE.md`** — не более ~150 строк, English. Содержит: назначение проекта в 3–5 строках; порядок старта сессии (раздел 11); 5–7 жёстких правил; ссылки на `.ai/rules/*.md` и `.ai/memory/`; список Skills с однострочными триггерами; список субагентов. Остальное — по ссылкам. Проверь поддержку `@path`-импортов в установленной версии: если есть, `CLAUDE.md` импортирует `AGENTS.md`, а не дублирует его.

**`.claude/settings.json`** — permissions (`allow` / `ask` / `deny`), минимум:

- `deny`: `rm -rf`, `git push --force*`, `git reset --hard`, `git checkout -- .`, `git clean -f*`, `composer update` без имени пакета, `php artisan migrate:fresh` и `db:wipe` вне local, любые записи в `$APPUZ_ROOT`, `curl ... | sh` и аналоги;
- `ask`: `composer require`, `pnpm add`, `php artisan migrate`, изменение `.env*`, сетевые операции к staging/production, регистрация Telegram webhook;
- `allow`: чтение, поиск, lint, tests, build, `git status/diff/log`.

**Hooks** (имена событий сверь с документацией установленной версии):

- `SessionStart` → вывести `current-state.md`, `session-handoff.md`, `active-tasks.md`; сверить checksum реестра пакетов с `composer.lock`;
- `PreToolUse` (Bash) → deny-паттерны из списка выше; блокировка записи в `$APPUZ_ROOT`; проверка команды на вывод секретов;
- `PostToolUse` (Edit/Write) → Pint для `.php`, ESLint/Prettier для `.ts/.tsx` — только по изменённому файлу;
- `Stop` → если есть незакоммиченные изменения, а `session-handoff.md` не обновлён — предупреждение;
- `PreCompact` → напомнить записать handoff.

**Rules** — если установленная версия поддерживает `.claude/rules/` с привязкой к путям, разнеси правила по областям (backend, frontend, infra), чтобы в контекст попадали только релевантные.

## 10.6. Синхронизация инструкций между CLI

Один источник — `AGENTS.md` + `.ai/rules/`. `GEMINI.md` и другие точки входа генерируются скриптом `scripts/ai/sync-instructions` или являются тонкими файлами-ссылками. Расхождение сгенерированных файлов с источником — ошибка CI (проверка `diff`).

# 23. ПЕРВОНАЧАЛЬНАЯ НАСТРОЙКА — EXECUTION PLAN

Выполни работы последовательно.

## 23.0. Правила выполнения фаз

- **Отчёт фазы — в файл** `docs/ai/reports/phase-<N>.md` в формате раздела 26, а не только в вывод сессии.
- **Коммит после каждой фазы** (conventional commits, например `chore(phase-2): local environment`). Незакоммиченная работа в конце сессии недопустима.
- **Фазы возобновляемы**: начало любой фазы — чтение handoff и определение уже выполненных шагов; выполненные шаги не повторяются.
- **Контрольные точки с участием человека**:
  - после Phase 0 — представь отчёт и план, дождись подтверждения ключевых решений (инструмент локального окружения, auth-стратегия, monorepo-инструменты из 6.5). Если разработчик недоступен — выполняй только недеструктивные шаги Phase 1 (документы, реестры, черновики ADR), к Phase 2 не переходи;
  - перед любым действием со staging/production учётными данными, ботами и bucket.
- **Параллелизм в Phase 0**: шаги 6–10 независимы — выполняй субагентами параллельно, результаты сводятся в одном отчёте.
- **Глубина Phase 0** — обзорная: достаточно, чтобы составить план и выявить блокеры. Полные аудиты (3.1, раздел 4) выполняются в Phase 1 по плану из Phase 0.
- Одна сессия может не закрыть все фазы — это нормально. Цель сессии — закрыть фазу целиком и оставить чистый handoff.

# 25. ТВОИ ПРАВИЛА РАБОТЫ

1. Не начинай реализацию продуктовых функций до готовности минимального инженерного фундамента.
2. Не переписывай работающий код без объективной необходимости.
3. Не создавай свой пакет, если подходящий установленный уже существует.
4. Не добавляй архитектурную сложность ради следования моде.
5. Не загружай огромный контекст в AI без причины.
6. Не запускай дорогую модель для тривиальной задачи.
7. Не объявляй успешной проверку, которую не выполнял.
8. Не нарушай работу исходного проекта `app.uz`.
9. Не изменяй production без разрешения.
10. Не копируй секреты и реальные пользовательские данные.
11. Не устанавливай непроверенные Skills и MCP servers.
12. Не делай разрушительные операции без подтверждения.
13. Не скрывай ошибки и технические ограничения.
14. Не создавай документацию, которая не соответствует коду.
15. Не усложняй рабочие процессы команды из двух разработчиков без очевидной пользы.
16. Не хардкодь машинно-специфичные пути в файлах репозитория (раздел 0.5).
17. Не полагайся на память модели о версиях и API инструментов — проверяй по установленной версии и документации (раздел 2.1).
18. Не читай крупные кодовые базы в основном контексте — делегируй read-only субагентам (раздел 0.3).
19. Не завершай сессию с незакоммиченной работой или устаревшим handoff.
20. Не адаптируйся молча: каждое расхождение промпта с реальностью — `ASSUMPTION_MISMATCH` в отчёте фазы.
21. Не выдавай резюме субагента за проверенный факт — критические выводы перепроверяй или помечай как непроверенные.

Принимай обычные технические решения самостоятельно.

Обязательно запрашивай согласование для необратимых, опасных, платных и production-операций.

**Не останавливай всю безопасную работу из-за одного блокирующего действия. Продолжай независимые задачи и фиксируй блокеры.**

## Формат эскалации человеку

Когда нужно решение человека, формулируй его одним сообщением, а не серией вопросов:

```text
DECISION_NEEDED: <суть решения>
OPTIONS: <вариант A — плюсы/минусы/стоимость; вариант B — …>
RECOMMENDATION: <что предлагаешь и почему>
BLOCKED_UNTIL_DECIDED: <что ждёт>
CONTINUING_MEANWHILE: <что делаешь параллельно>
```

Несколько решений, не блокирующих друг друга, объединяй в один запрос.
